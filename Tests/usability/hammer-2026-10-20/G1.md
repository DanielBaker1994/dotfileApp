# G1 - completion / snippet soak (2026-10-20)

## Baseline
- Editor = embedded nvim (SwiftTerm); popup = nvim native pum fed by vim/snippets.lua. Trigger: type >=2 chars of any
  substring of a snippet prefix in insert mode (TextChangedI -> popup(), snippets.lua:~55). Tab accepts (first item when
  noselect), CompleteDone -> expand_chosen() -> vim.snippet.expand.
- NOT exposed in socket `state` (vimMode is ""). Oracle used: the sandbox nvim's own --listen socket (read-only
  --remote-expr: mode(), pumvisible(), vim.snippet.active()). `pane-shot` is unusable here (needs herdr); used `window-shot`.
- Works at first: typing `bash` shows `markdown_bash_block [snippet]` (shots/G1-popup-visible.png); typing `bash`+Tab in one
  fast call expands the code-block snippet (shots/G1-popup-accept.png).

## F1 - S2 - 10/10 - insert mode (and the popup with it) is killed about once a second when the editor RPC is unreachable
Trail (all with real keys, no perturbation needed): esc; shift+g o (insert); b a s h; wait 0.5-1.5s, nothing else.
Expected: stays in insert mode with the popup up until I act. Actual: mode goes i/ic -> n within ~0.4-1s, popup gone,
subsequent typed letters run as normal-mode commands (`s`,`b`,`a`...), so completion "stops working" (shots/G1-popup-gone-normal-mode.png).
Also happens with no popup (typing `zz`, no snippet match): any idle insert session ends. Reproduced 6/6 by key, 2/2
by nvim --remote-send (so not a ks-input artifact).
Diagnosis: a vim.on_key log in the sandbox nvim shows the app injecting `<C-\><C-N>:silent! checktime | echo ''<CR>` roughly
every second.
Cause (host.rs:4560 poll_notes_vim, once/sec) -> VimPane::command (notes_vim.rs:611): it tries
`eval("execute('silent! checktime')")` over the nvim RPC socket and, on ANY RPC failure/timeout, falls back to
`remote()` which sends the Ex command as typed keys prefixed with `<C-\><C-N>` - that leaves insert mode, closes the pum and
cancels a snippet session. Here the RPC always fails: the sandbox nvim socket path
(`.../mcp-sandbox/home/.cache/kitchen-sink/nvim-notes-37128.sock`) is 105 chars; AF_UNIX max is 103 on macOS
(python connect -> "AF_UNIX path too long"), so NvimRpc::connect fails every time and the keys fallback fires every second.
Relevance to the owner's "completion randomly stops": in the real app the path is short so RPC normally works, but ANY single
RPC miss (eval timeout RPC_TIMEOUT=1s while nvim is busy, e.g. big note / slow render-markdown redraw, dropped connection after
nvim restart, hit-enter prompt) takes the same fallback and silently drops the user out of insert mode mid-completion. The
background poll must never inject keys. Suggested fix: for the periodic checktime (and flush) skip on RPC failure instead of
`remote()`; or send via `nvim_command` only; or if keys needed use `<Cmd>silent! checktime<CR>` (does not leave insert).
Same `<C-\><C-N>` fallback pattern exists in command()/open()/shutdown() (notes_vim.rs:~611, 640, 683).
Secondary: sandbox launcher should use a shorter nvim socket path (TMPDIR/HOME under .build/mcp-sandbox is too long), otherwise
every GUI-sandbox editing session is broken the same way.

## F2 - S3 - tooling note (not an app bug as far as verified)
`ks-input key` drops a lone key in a single-key call (o, i, x), and keys sent right after `esc` in the same call are lost
(Esc+key = Alt-key in the terminal). Use >=2 keys per call and a >=0.5s wait after esc.
